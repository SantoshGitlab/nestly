## STATUS

own blocker — *"a connected Chrome extension with localhost permission,
which is a human/tooling action I cannot grant myself"* — no longer applies:
this run used real Playwright-driven browser automation against live
frontends, backends and a live Postgres instance, following the
[e2e-check skill](../.claude/skills/e2e-check/SKILL.md)'s five-phase
protocol in full. QA-REPORT-2026-08-07.md's static findings (S1–S11) are

This document is a **synthesis**, per the e2e-check skill's own final-step
instruction to the lead: *"combine all subagent reports... not re-test."*
Full per-feature checklists live in this run's own session record; what
follows is verdicts, defects, and what remains open.

## VERDICT: CONDITIONAL GO

The core booking flow — the product's central transaction — was verified
working correctly end-to-end across all three services for the first time
this project has evidence of: a real customer booking, created through the
real UI, appears with matching data in admin-web and provider-web, not just
in the database. Several real defects were found during the sweep and fixed
live, not just logged. This is a materially different position than
2026-08-07's "absence of evidence."

It is **conditional**, not unconditional, because two confirmed defects
below (payments RBAC, pincode validation mismatch) should be fixed first,
and one design question (auto-assignment) should be answered before
launch — none of them were known before this sweep; all three are now
filed as tasks. Nothing found is architectural or requires redesign.

## PHASE-BY-PHASE RESULTS

### Phase 0 — Environment sanity: GO

Postgres/Redis up, all three APIs returning real responses, no port
squatters, CORS matching each frontend's actual origin.

### Phase 1 — Seed data coverage

Found and fixed: **zero rows existed in `service_pincode_mapping` and
`slot_window_rule` for any seeded city**, and two of the seeded city rows
used 6-character hex strings instead of valid pincodes — meaning no
customer could book *any* service in this database before this sweep, in
any environment using this seed set. `SlotAvailabilityService` and
`SlotWindowRepository` both fail closed by design (an unmapped
service/pincode or a window with no rule row is correctly treated as
unbookable, not a bug in that code) — the bug was purely in what got
seeded. Fixed by adding one zone and one locality per existing city, then
adding real slot-window and service-pincode-mapping rows through the actual
admin-web UI (not a script), which is also how this gap would be fixed in a
real deployment.

Also cleaned up: stale smoke-test data from an earlier session (4 bookings
and their child rows, 3 test-labeled provider rows) that had been created
by direct SQL/construction rather than through the real assignment service.
This data was the root cause of what looked, mid-sweep, like a "[High]
booking status desync" defect in provider-web — verified by reading the
actual `AssignAsync` code (correct) and tracing every affected row back to
that leftover data via direct DB query, not assumed. **Recorded here so
this false positive is not later miscounted as a real defect**: the
assignment code itself was never wrong.

### Phase 2 — Feature inventory (3 apps)

Completed: route and interactive-feature checklists built for customer-web,
admin-web and provider-web, cross-referenced against `docs/SRS.md` and
`docs/API.md`.

### Phase 3 — Browser walkthrough (3 apps)

**customer-web**: walked end-to-end once the Phase 1 locality/zone gap was
fixed (that gap had been blocking every booking attempt).

**provider-web**: walked in full. Fixed live:
- `frontend/provider-web/src/hooks/useJobStatusLive.ts` — missing
  `withCredentials: false` on the SignalR tracking-hub connection was
  silently killing live job-status sync (a CORS preflight failure).
- `frontend/provider-web/src/lib/jobs-api.ts` — `getCompletionVerification`
  returned `undefined` for a 204 response, which React Query v5 forbids as
  resolved query data; now coalesces to `null`.
- `frontend/provider-web/src/app/(provider)/jobs/[id]/page.tsx` — widened a
  prop type to match the fix above.

**admin-web**: walked in full — every route, every modal, every gated
action. Fixed live:
- `frontend/admin-web/src/components/ui.tsx` — `controlId()`'s fallback
  used a label-derived id, so two same-labeled fields on one page (e.g.
  bookings/[id]'s Cancel "Reason" vs. Refund "Reason") collided on the same
  DOM `id`. Fixed with `useId()`, which is unique per component instance.
  **This file is intentionally byte-identical across all three apps**
  (its own header comment says so) — only admin-web's copy was fixed this
  session; the same bug is very likely still live in customer-web's and
  provider-web's copies. Filed as a known gap below, not fixed blind
  without re-verifying each app's own usage.
- `frontend/admin-web/src/app/(admin)/settings/page.tsx` — 4 of 7 settings
  groups (Booking rules, Tax, Wallet, Coupon) could not be saved at all
  while their nullable field was left at its current, unset (blank)
  value — `register(name, { setValueAs })`'s transform never runs on an
  untouched field, so its raw `""` failed the nullable-number schema
  silently (no toast, no network request). Fixed by moving those 4 fields
  to `Controller`-bound components; verified all 7 groups now save and
  persist `null` correctly.

Found, **not fixed** (reported, out of frontend scope):
- `GET /api/v1/admin/payments` 403s for the Super Admin dev account,
  contradicting `AdminPermissionCatalog`'s own documented claim that Super
  Admin has full access to every module. Root cause confirmed in the
  database: `admin_permission` has zero rows for `module='payments'`, and
  no seed migration populates that table at all — rows are only created
  lazily when an admin edits a role's permission matrix through the UI.
  This is a **general seeding gap affecting every module added after the
  original seed migration was written**, not something specific to
  payments, and it means a fresh deployment's Super Admin cannot actually
  see every module until someone manually opens the permissions UI for
  each one — inconsistent with what the platform claims about that role.
  Filed as `tasks.csv` **#332**.

### Phase 4 — Cross-service consistency: PASS

A real booking created as a customer (service, price, slot, address) was
confirmed matching field-for-field in admin-web (after a manual status
transition and manual provider assignment — see below) and in provider-web
once assigned. No 4xx/5xx or contract-shape mismatches observed across the
three services during this flow.

Found during this phase:
- **[Medium, design gap, not fixed]** No automatic Confirmed →
  AwaitingFulfilment transition exists anywhere in the backend — grepped
  across all non-test code. Admin-web's own UI copy states *"the system
  auto-assigns the nearest eligible one when a booking reaches Awaiting
  Fulfilment,"* but nothing today moves a booking into that state
  automatically; an admin must manually run "Update status → Preparing
  Service" first. Either the UI copy overstates current behaviour, or a
  scheduled/event-driven transition is genuinely missing. Filed as
  `tasks.csv` **#333** for a product decision, not assumed either way here.
- **[Low, not fixed]** `frontend/customer-web/src/components/AddressForm.tsx`
  enforces a strict `^\d{6}$` pincode regex client-side; the backend
  (`AddressValidators.cs`) only requires non-empty, ≤12 characters. This
  seed database's own city pincodes (`e873fb`, `217d53`) are hex strings
  that fail the frontend's regex, meaning the UI cannot address-match this
  DB's own serviceable areas without a direct API call bypassing the form.
  Filed as `tasks.csv` **#334**.
- **[Low, not fixed]** `provider-web`'s job detail page calls
  `GET /jobs/{id}/completion-verification` unconditionally, 404ing for
  every non-Completed job. Harmless (swallowed by React Query, no visible
  error) but noisy — an `enabled` gate on job status is the fix. Filed as
  `tasks.csv` **#335**.
- **[Low, reported, not root-caused]** A SignalR negotiation failure to
  `hubs/tracking` on provider-web's job detail page, no visible functional
  impact. Possibly an artifact of running all six services as bare
  processes in this sandbox rather than the intended container topology —
  not confirmed as a real defect either way.
- **[Informational]** Two distinct `city` rows are both named "Bengaluru"
  (different `state_id`, both "Karnataka"), indistinguishable in the city
  picker — a seed-data hygiene issue, left as-is since other concurrent
  work in this shared database may depend on it.

## RECOMMENDATION

**Fix before launch**: #332 (payments RBAC — quick, a seed migration
populating `admin_permission`/`role_permission_mapping` for existing
modules) and #334 (pincode validation — a one-line regex relaxation or a
backend-driven format). **Decide before launch**: #333 (auto-assignment —
either build the missing transition or correct the UI copy that implies it
exists). Everything else in the bug list is low-severity and can ship
alongside a fix, not gate it.

The booking funnel itself — the product's core transaction — is sound
across all three services. This is the evidence QA-REPORT-2026-08-07.md's
NO-GO was withheld pending; task 318 is complete.
